# UniVR-RIFE rolling-shutter unrolling on trn2 — self-contained reproducer

One script, `repro_unrolling_trn2.py`, plus the inputs and reference it needs. No repository, no
package install, no framework beyond `torch`, `numpy` and `PIL` (`nki` is imported only on the device
path). Everything below was measured with the exact files in this bundle.

The workload is **gather-bound**: 62.1% of a forward is a data-dependent bilinear resample that
lowers to software-generated DMA descriptors moving 24 B each. That is the reason for this bundle.

## 4. What the model computes

A rolling-shutter sensor reads one scanline at a time, so row `y` corresponds to a different instant
than row `y+1` and moving content is sheared. For readout ratio `γ` and normalised target time `t`:

```
τ(y) = t + γ − γ·y/H + 1e-4          # one value per scanline, constant along x
```

Production uses `γ = 0.98`. The goal is the global-shutter frame — what the sensor would have
captured with every row exposed at one instant.

This is posed as **frame interpolation with a per-row target time**. Given consecutive RS frames
`I0`, `I1`, estimate bidirectional flow, resample both toward `τ(y)`, and blend. Because `τ` varies
by row, every output row is interpolated to a different instant, which is what removes the shear.
The network is RIFE's `IFNet_m` with `τ` as an extra input channel.

```
flow, mask = None, None
for i, block in enumerate([block0, block1, block2]):     # coarse->fine, scales 4, 2, 1
    if flow is None:
        flow, mask = block(concat(I0, I1, tau), None, scale=s_i)
    else:
        dflow, dmask = block(concat(I0, I1, tau, W0, W1, mask), flow, scale=s_i)
        flow, mask   = flow + dflow, mask + dmask         # residual refinement
    W0 = warp(I0, flow[:, 0:2])                           # I0 -> target time
    W1 = warp(I1, flow[:, 2:4])                           # I1 -> target time
    merged_i = W0*sigma(mask) + W1*(1 - sigma(mask))      # learned soft blend

c0  = contextnet(I0, flow[:, 0:2])                        # 4 pyramid levels, each warped
c1  = contextnet(I1, flow[:, 2:4])
res = unet(I0, I1, W0, W1, mask, flow, c0, c1)[:, :3]*2 - 1
out = clamp(merged_2 + res, 0, 1)
```

`flow` is 4-channel: `[0:2]` maps `I0 -> t`, `[2:4]` maps `I1 -> t`.

### Triplet composition

One output frame per input frame needs two passes over three inputs:

```
rows [0, H/2)    <- BACKWARD pass over (I_k,   I_k+1) at t = -γ/2    = -0.49
rows [H/2, H)    <- FORWARD  pass over (I_k-1, I_k  ) at t = 1 - γ/2 = +0.51
```

Each output row comes from exactly one pass, so a tile lying wholly on one side of `H/2` needs one
pass rather than two. Exact, not an approximation.

### Tiling

A 4K frame (1728×4096) does not compile as one graph, so it is split 2×4 = 8 tiles, one per core.
Valid extents are 864×1024 and partition the frame exactly. Each tile is *read* with a 128 px halo,
because the model has a receptive field and a tile computed without surrounding context is wrong near
its edges. That gives padded shapes 992×1152 and 992×1280.

The halo is a correctness requirement, not margin: measured maximum flow displacement at 4K is
**43.28 px**, and the figure is resolution-dependent (6.29 px at 992×1280), so a halo validated at
reduced resolution does not transfer to 4K.

One subtlety that fails silently: `τ` depends on the **absolute** scanline in the frame. A tile
starting at absolute row 864 must use rows 864… over the full frame height, not 0… over the tile
height. Get it wrong and the output still looks plausible while disagreeing with the untiled
reference. Verified tiled == untiled at 117.4 dB, 0 pixels unwritten, 0 written twice.

## 5. The resample, and why it dominates on trn2

For every output pixel and channel:

```
sx = clamp(x + fx, 0, W-1)      sy = clamp(y + fy, 0, H-1)
x0 = floor(sx)   y0 = floor(sy)   ax = sx - x0   ay = sy - y0

out[c,y,x] = (1-ax)(1-ay)*I[c, y0,   x0  ] + ax(1-ay)*I[c, y0,   x0+1]
           + (1-ax) ay  *I[c, y0+1, x0  ] + ax* ay  *I[c, y0+1, x0+1]
```

A 4-tap bilinear fetch at a **flow-dependent fractional** coordinate. There are **14 per forward**:

| site | count | channels | resolution |
|---|---|---|---|
| IFBlock image warps (`W0`, `W1` × 3 blocks) | 6 | 3 | full |
| Contextnet feature warps (4 levels × 2 images) | 8 | 16 / 32 / 64 / 128 | /2 /4 /8 /16 |

Stock PyTorch expresses this as `F.grid_sample`. The port replaces it with an explicit indexed gather
over an `[H·W, C]` layout — identical arithmetic, verified `cos = 1.000000`.

The problem is the address. `y0·W + x0` is computed from the flow, which is an **activation**, so the
address is not known until the previous layer has run. A data-dependent gather cannot reach the
hardware descriptor generator on trn2, so GpSimd builds every descriptor in software, and the cost is
**per descriptor, not per byte**.

Measured on one full-resolution warp NEFF at 992×1280 (1,269,760 output pixels):

```
sw_dyn_dma_packets   2,539,520      = exactly 2.0000 descriptors per output pixel
total_time_us         68,719.8      = 37.0 M descriptors/s, i.e. ~27 ns per descriptor
payload                     24 B    = 2*C*4 at C=3   ->  ~0.89 GB/s effective
tensor_active_%            0.0
sw_dyn_dma_active_%       97.3
hw_dyn_dma_active_%         0
```

The kernel issues two descriptors per output pixel: one gathers the top pair `(x0, x0+1)` and one the
bottom pair, each `2*C` contiguous elements, with the blend done in SBUF on the Vector engine. So the
descriptor count is structural, and at `C=3` the payload is 24 B against a DMA efficiency target
around 512 B.

The six full-resolution `C=3` warps are ~90% of all warp time and are precisely the case a custom
kernel cannot rescue — the payload is too small to amortise descriptor cost. A GPU performs this in
fixed-function texture hardware; Trainium has no equivalent, so one texture instruction becomes a
software descriptor build.

## 6. Reproducing individual pieces

```bash
# resample numerics only, CPU, no assets, seconds
python repro_unrolling_trn2.py --self-test

# descriptor accounting from shapes alone: no model, no data, no device
python repro_unrolling_trn2.py --report-only --height 1728 --width 4096

# per-block attribution (needs --compile none; barriered, upper bounds)
python repro_unrolling_trn2.py ... --per-block

# score against the stock CPU fp32 grid_sample reference with identical weights
python repro_unrolling_trn2.py ... --gate
```

`--warp` selects the resample implementation:

| value | what it is |
|---|---|
| `gridsample` | stock `F.grid_sample`, the numerical reference |
| `gather` | portable explicit gather |
| `nki` | the trn2 kernel, 2 descriptors/pixel, best runtime, 80–100 min compile per 4K shape |
| `nki-dyn` | device-loop variant, compiles in seconds, ~1.1–1.3x slower |
| `window` | dense reformulation with no indirect access — exact, and measurably slower; kept so that suggestion can be costed rather than argued about |

`--dtype bf16` runs throughout in bf16 and holds ~54 dB / 2.7 LSB, which passes the 3 LSB bar but has
far less headroom than fp32's 98–104 dB.

## 7. Known issues on this stack

Encountered while producing the numbers above. Items 1 and 2 are compiler/runtime defects; 3–5 are
constraints we worked around; 6 is the substantive ask.

1. **Repeat-invocation lazy-materialization failure.** A second forward can die with
   `RuntimeError: Failed to generate prologue: Failed to merge transformation chain 5`, raised from
   `LazyTransformationManager.cpp:270` with `Prologue generation failed op= aten::cat`, surfacing at
   `F.interpolate` inside an IFBlock. The first forward completes correctly. Intermittent: it
   reproduces reliably under `NEURON_RT_INSPECT_ENABLE=1`, and also without it at `--cores 2`.
   Workaround: `--iters 0` for a single-shot run.

2. **Shape-dependent StableHLO conversion failure.** Padded shapes 896×1056 and 896×1088 fail with
   `KeyError: 'torch_mlir.dialects.builtin'` in
   `neuron_dynamo_backend/utils/stablehlo_utils.py:171` (`parse_module_io`, via
   `convert_fx_to_stablehlo`). The 992×1152 and 992×1280 shapes used above compile fine, so this
   blocks configurations rather than the whole path.

3. **`nn.PReLU` cannot be legalised under `torch.compile`** — `failed to legalize operation
   'torch.operator'`. It lowers fine in eager. Replaced with `relu(x) - w*relu(-x)`
   (`--neuron-prelu`), verified bit-exact (PSNR inf, 0.00 LSB).

4. **`torch.compile` requires `fullgraph=True` here.** Without it dynamo graph-breaks silently, and a
   break around the `view(torch.uint32)` index bitcast in the warp corrupts which pixels are sampled:
   55.37 dB / 42.70 LSB instead of eager's 121.78 dB / 0.00 LSB. With `fullgraph=True` every compiled
   mode matches eager exactly. Compiling does **not** reduce graph count on this backend — at 256×384
   it went from 133 NEFFs eager to 193 — so the reproducer defaults to `--compile none`.

5. **Synchronous tensor I/O.** The runtime logs
   `nrta_tensor_read currently uses a synchronous implementation underneath. Asynchronous tensor I/O
   will be added in a future runtime release.` A host read is therefore the only true completion
   barrier, which is what the timing harness uses.

6. **Descriptor economics of the data-dependent gather.** 2 descriptors per output pixel at 24 B each,
   ~27 ns per descriptor, ~0.89 GB/s effective, 97.3% software-dynamic DMA with the Tensor engine at
   0.0% and hardware DGE unused. This is 62.1% of the forward and is the reason trn2 sits far from the
   CUDA reference on this model. The questions we would like to work through:
   - can a data-dependent gather reach the **hardware** descriptor generator, or is software DGE
     structural on trn2?
   - is there a way to raise bytes per descriptor beyond `2*C*4`, given `C=3` is fixed by the model?
   - is there a supported path to overlap descriptor generation across warps, or across cores, given
     eight cores currently return 3.82x?
