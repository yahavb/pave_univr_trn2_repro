# Tiling, halo, and what one fused graph contains

Reference for the two things that decide whether `--compile whole` succeeds: how a frame
becomes tiles, and what ops end up inside one tile's graph. Every number here is either
taken from the code or from a measured run, and marked which.

---

## 1. Why the frame is tiled at all

1728x4096 does not compile as one graph. It is split into `ny x nx` **valid extents**
that partition the frame exactly — no overlap, no gaps — and each is dispatched to one
NeuronCore. `build_replicas()` builds one model replica per core and a
`ThreadPoolExecutor(max_workers=ncore)` runs them.

**Consequence that is easy to get wrong: the frame is NEVER one graph, at any tile
size.** Tiles are separate graphs on separate cores by construction. `--compile whole`
fuses **one tile's forward**, not the frame. Shrinking the tile does not move toward a
single-frame graph, because that is not a thing this design can produce.

---

## 2. The halo

A tile owns its valid extent but cannot be computed from it alone: convolutions read
neighbours, and the flow-guided resample reads wherever the flow points. A pixel at the
tile edge needs data from outside it.

So each tile is **read** with `halo` px of extra context on every side, computed over
that larger region, and only the valid part is kept. The margin is the halo.

```
  valid extent   864x1024   <- what this tile owns and writes
  + halo 128     each side
  -> padded      992x1280   <- what the model actually runs on
```

Two consequences, both load-bearing:

* **The halo is overlap, so it costs real work.** Neighbouring tiles both read the same
  halo pixels. That is the entire "total pixel work" penalty of finer grids.
* **The halo sets the padded size, and padded size is what the compiler rejects.** See
  section 6.

### 2.1 The exact algorithm

From `plan_tiles()` and `_align_window()`:

```
vh = ceil(H / ny)                    valid tile height
vw = ceil(W / nx)                    valid tile width
for each tile at valid origin (oy, ox):
    vy = min(vh, H - oy)             clipped at the frame edge
    vx = min(vw, W - ox)
    py0 = max(0, oy - halo)          padded window, clipped to the frame
    px0 = max(0, ox - halo)
    py1 = min(H, oy + vy + halo)
    px1 = min(W, ox + vx + halo)
    align [py0, py1) and [px0, px1) up to a multiple of TILE_ALIGN = 32
```

`_align_window` grows the window — preferring to extend *inside* the frame, then
outward — because extending only reads more context, which the halo already does. If it
cannot align within the frame it raises rather than producing silently wrong flow. Its
own error text gives the reason for the 32: *"the model's coarse IFBlock scale has an
effective stride of 16 and the upsample must round-trip exactly."*

**Edge tiles are smaller than interior tiles**, because the padded window is clipped at
the frame boundary. That is why a grid has several distinct padded shapes, not one.

### 2.2 Halo is quantised, so most values are equivalent

`TILE_ALIGN = 32` snaps the padded window, so halo moves in steps. Measured on the real
planner at 4x8:

| halo | largest padded shape | px |
|---|---|---|
| 44, 45, 48 | 544x608 | 330,752 |
| 50 | 544x640 | 348,160 |
| 64 | 576x640 | 368,640 |
| 72 | 576x672 | 387,072 |
| 80 | 608x672 | 408,576 |
| 96 | 640x704 | 450,560 |
| 128 | 704x768 | 540,672 |

So setting halo 43.28 buys nothing over 48 — 44, 45 and 48 all produce the identical
544x608 tile. Beyond that the steps are finer than a single 32-px quantum in each axis,
because H and W align independently.

**These values come from `plan_tiles()` itself, not from a reimplementation of it.** An
earlier hand-rolled version of the alignment rule produced a different table (it had
50..64 collapsing to one step and 72/80 sharing 608x704); it agreed with the real planner
on the shapes that had been measured on device but diverged elsewhere. Any future halo
table should be generated by calling `plan_tiles` directly.

### 2.3 How much halo is actually required — UNRESOLVED

`REPRO_README.md` calls the halo *"a correctness requirement, not margin"* and cites
**43.28 px** max flow displacement at 4K. This repo contains three different values for
that one quantity:

| figure | source |
|---|---|
| 43.28 px at 4K, 6.29 px at 992x1280 | REPRO_README |
| 2.33 px at 992x1280 | STATE.md, "the bundle's 43.28 px figure does NOT hold for this frame pair" |
| **29.02 px** max over all 112 resample calls | measured, `--record-flow` |

Displacement is also not the whole requirement: the conv receptive field reads outside
the tile too, and **nobody has quantified that contribution**. So the halo requirement
is not known from first principles. It has to be settled by scoring accuracy against
`ref_cuda_fp32_1728x4096.npy` at `--bar 3` — and it fails *silently*, as edge artefacts
that look plausible while disagreeing with the untiled reference.

Halo 64 clears the largest of the three figures by ~48%.

## 3. What one fused graph contains

With `--compile whole` and `torch.compile(backend="neuron", dynamic=False,
fullgraph=True)`, one graph holds the entire forward of one tile. `fullgraph=True` means
a dynamo break raises rather than silently falling back, so this is one real graph — the
script prints `1 graph over the whole forward`.

### Pyramid — 3x IFBlock, scales 4, 2, 1

`block0(in=7, c=240)`, `block1(in=18, c=150)`, `block2(in=18, c=90)`. Each block:

```
  interpolate x down by 1/scale          (and flow down by 1/scale, scaled by 1/scale)
  cat(x, flow)                            when flow is not None
  conv0:      conv stride 2 -> conv stride 2      (input /4 from here)
  convblock:  8 convs at constant channels, then + x   (residual)
  lastconv:   ConvTranspose2d(c, 5, 4, 2, 1)
  interpolate up by scale*2
  -> flow = tmp[:, :4] * scale * 2 ,  mask = tmp[:, 4:5]
```

then, inside the same stage (`_StageFirst` / `_StageNext`):

```
  2 warps at FULL tile resolution:  w0 = warp(img0, flow[:, :2])
                                    w1 = warp(img1, flow[:, 2:4])
```

The warps live **inside** the stage module deliberately. The code comment records why:
when `--compile split` wrapped only `block0/1/2`, the six full-resolution warps sat in
`IFNet_m.forward` *between* the blocks, outside every compiled region, so ~60% of the
frame stayed eager and the mode bought nothing. **Compiling a stage only helps if the
stage owns its warps.**

### Refinement

```
  Contextnet(img0, flow[:, :2])      4 levels, each:  Conv2 -> interpolate flow x0.5 -> warp
  Contextnet(img1, flow[:, 2:4])     same, so every Contextnet op runs TWICE per forward
  Unet(img0, img1, w0, w1, mask, flow, c0, c1)
       4x Conv2 down (17->32, 64->64, 128->128, 256->256)
       4x deconv up  (512->128, 256->64, 128->32, 64->16)   with skip concatenations
       final Conv2d(16, 3) -> sigmoid
  sigmoid x3 on the masks
  blend:  merged[i] = a * m + b * (1 - m)      for i in 0..2
  clamp(merged[2] + res, 0, 1)
```

`Conv2(i, o, stride=2)` is two convs: `conv(i, o, 3, stride, 1)` then `conv(o, o, 3, 1, 1)`.
`deconv(i, o)` is `ConvTranspose2d(i, o, 4, 2, 1)` + PReLU.

**PReLU is substituted** under `torch.compile`: `relu(x) - w*relu(-x)`, because `nn.PReLU`
cannot be legalised by the Neuron backend. The identity is exact, so no accuracy is
traded.

### Counts per tile-forward

| | count | detail |
|---|---|---|
| **warps (resamples)** | **14** | 6 at C=3 full res (3 blocks x 2 images), 8 in Contextnet at C=16/32/64/128 and /2 /4 /8 /16 |
| convs + deconvs | **54** | 33 IFBlock, 8 Contextnet, 13 Unet |
| interpolate | ~14 | down/up per block, plus flow /2 per Contextnet level |
| MACs | **188.35 G** | at the 992x1280 tile |

The 54 is verified against the checkpoint: exactly 54 four-dimensional weight tensors
excluding the 11 training-only `block_tea` ones, with channel counts matching on
spot-checks including `ConvTranspose2d`'s transposed `(in, out)` layout.

A **triplet is 2 forwards** — forward on `(rs0, rs1)` at t=+0.51, backward on
`(rs1, rs2)` at t=-0.49, merged with rows above 864 from the backward pass. So 28
resamples and 108 convs per tile per frame.

## 4. Graph count follows SHAPES, not tile count

The script prints its own inventory:

```
  padded tile shapes: 992x1152, 992x1280  -> 2 distinct graph(s) per timestamp
  x2 timestamps (triplet)                 -> up to 4 graphs to compile
```

So 8 tiles at 2x4 need only **~4 graphs**, because the 8 tiles reuse 2 distinct padded
shapes and a triplet runs 2 timestamps. Every additional distinct shape adds graphs.
Measured shape counts from the real planner:

| grid | halo | tiles | shapes | largest | total px | vs 2x4 h128 |
|---|---|---|---|---|---|---|
| 2x4 | 128 | 8 | 2 | 992x1280 | 9,650,176 | 1.00x |
| 4x8 | 128 | 32 | 4 | 704x768 | 15,073,280 | **1.56x** |
| 4x8 | 64 | 32 | 4 | 576x640 | 10,862,592 | **1.13x** |
| 2x8 | 64 | 16 | 2 | 928x640 | 9,265,152 | **0.96x** |

The `total px` column is the halo cost made explicit: it is the sum of every padded tile,
so it counts halo pixels once per tile that reads them. Note the direction — **4x8 at
halo 64 does LESS total work than 4x8 at halo 128** (1.13x vs 1.56x), and 2x8 at halo 64
does less than the 2x4 halo-128 baseline. Finer grids are not automatically more
expensive; the halo is what makes them expensive.

**The prize:** an eager run (`--compile none`, which is what `repro-job.yaml` does since
it passes no `--compile`) caches **275 NEFFs**. Fused would be ~4-8.

## 5. `--only-tile N` does not mean "a representative tile"

Both compiler limits scale with padded pixels, so **the largest padded shape is the
binding constraint**. An 8-core run compiles every distinct shape, so a verdict from one
tile only generalises if that tile is the largest.

Tile 1 is **not** always the largest. From the real planner:

| grid | halo | largest tile index | shape |
|---|---|---|---|
| 2x8 | 64 | 1 | 928x640 |
| **3x9** | 128 | **10** | 832x736 |
| **4x8** | 64 | **9** | 576x640 |
| **4x8** | 128 | **9** | 704x768 |

This cost several runs: `--only-tile 1` at 4x8 halo 128 compiles 576x768 and **fuses**,
while the largest shape 704x768 is **rejected** with `in=7,569,408`. A false "4x8 FUSES"
verdict stood until the largest tile was tested.

To regenerate any table in this document, ask the planner rather than reimplementing it:

```bash
python3 - <<'PY'
import importlib.util, sys
spec = importlib.util.spec_from_file_location("m", "repro_unrolling_trn2.py")
m = importlib.util.module_from_spec(spec); sys.modules["m"] = m; spec.loader.exec_module(m)
for ny, nx, halo in [(2, 4, 128), (4, 8, 128), (4, 8, 64), (2, 8, 64)]:
    t = m.plan_tiles(1728, 4096, ny, nx, halo)
    shapes = sorted({(x["ph"], x["pw"]) for x in t})
    i = max(range(len(t)), key=lambda k: t[k]["ph"] * t[k]["pw"])
    tot = sum(x["ph"] * x["pw"] for x in t)
    print("%dx%d halo%-4d tiles=%-3d shapes=%-2d largest=tile %-2d %dx%d  total_px=%d"
          % (ny, nx, halo, len(t), len(shapes), i, t[i]["ph"], t[i]["pw"], tot))
PY
```

## 6. Why 14 is the whole story

The whole-graph rejection is:

```
[NCC_EBIR033] Number of elements in dimension 0 of InstDMACopy's input and dimension 0
of output AccessPatterns must match, but got in=17776640 and out=128
```

and

```
  17,776,640 = 1,269,760 px (992x1280 padded tile) x 14 resamples per forward
         128 = chosen by the BACKEND, not by the model
```

Under whole-graph fusion the backend forms **one `InstDMACopy` spanning all 14
resamples**, then cannot reconcile it against a 128-element output access pattern.
`out=128` appears even with stock `F.grid_sample`, so it is not something the model asks
for. The failure is **independent of the resample implementation** — `gather`,
`gridsample` and `nki-dyn` all produce the identical error, operands, and failing
instruction `I-21406-0_VN_0`.

So the operand is `padded_px x 14`, which makes it a **threshold, not a wall**, and
padded_px is set by valid extent + halo. That is the entire reason halo is the lever.

There is a second, independent limit:

```
[NCC_EBVF030] Instructions generated by compiler 6013317 exceeds the typical limit of
5000000
```

which barely responds to tile size at all — 2x8 at 761,856 px gave 5,988,611 and 2x12
at 634,880 px gave 5,983,171, so a 17% pixel cut bought 0.09% fewer instructions. It is
dominated by the fixed conv/U-Net structure of section 3, not by the tile.

The two limits move in opposite directions as the tile shrinks, and the measured verdicts
are in `STATE.md`. The only geometry known to fuse is **4x8 at halo 64**, largest shape
576x640, operand 5,160,960.
